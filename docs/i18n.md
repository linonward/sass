# Internationalization

Built on [next-intl](https://next-intl.dev). Routes live under `src/app/[locale]/`. The default locale has no prefix (`/pricing`); other locales are prefixed (`/zh/pricing`).

## Adding a language

Using Chinese (`zh`) as the example. No code changes are needed:

1. Add `"zh"` to `locales` in `src/core/i18n/locales.ts`:

   ```ts
   export const locales = ["en", "zh"];
   ```

   (There's a reason the locale list lives in this file rather than in `site.config.ts`: client components reference `routing.ts` via `core/i18n/navigation.ts`, and `site.config.ts` goes through zod validation, so putting the list there would drag the whole config schema into every page's client bundle. `site.config.ts` reads from this small file, so it's still the single source of truth. See the comments in that file for details.)

2. Copy `messages/en.json` to `messages/zh.json` and translate the values, keeping the keys unchanged.
3. Run `pnpm test` to confirm that `messages/zh.json` and `en.json` have the same keys.
4. Run `pnpm dev` and open `/zh` to check the pages.

With two or more locales, a language switcher appears in the header.

Write locale codes in BCP 47 (`zh`, `zh-TW`, `pt-BR`). The switcher shows each language's own name for itself (Deutsch, Français), generated by the browser's `Intl.DisplayNames`.

## Browser language

When someone visits an **unprefixed** URL (`/`, `/pricing`, `/blog/xxx`), the locale is decided in this order (`localeDetection`, configured in `src/core/i18n/routing.ts`):

1. The locale prefix in the URL: `/zh/pricing` is always Chinese and is never rewritten
2. The locale cookie: the user **explicitly switched** languages
3. `Accept-Language`: the browser language; if none of the supported locales match, fall through to step 4
4. The default locale

When step 3 matches, the response is a 307 to the prefixed URL (`/` → `/zh`, `/pricing` → `/zh/pricing`). **It's 307, not 301/308**: language preferences change, and a permanent redirect gets remembered by browsers and search engines with no way to undo it. The redirect response carries `Vary: Accept-Language` so a CDN doesn't cache the redirect for a Chinese visitor and serve it to an English one (only the redirect can carry this header: Next rebuilds the `Vary` of 200 responses; the body of a 200 doesn't depend on the browser language anyway, since an unprefixed 200 is always the default-locale page).

**Only an explicit switch is remembered.** Opening a shared `/zh` link does **not** write the cookie; otherwise an English visitor who clicks the wrong link once would be sent to the Chinese site on every later visit to `/`. Only the language switcher writes the cookie (`src/core/i18n/locale-switcher.tsx`, shared by the header and the dashboard user menu). next-intl's middleware would otherwise write one on its own whenever a prefixed URL is visited; `src/proxy.ts` removes it.

If you don't want automatic redirects, turn them off (for example, for a multilingual site where you don't want URLs rewritten) in `src/core/i18n/routing.ts`:

```ts
localeDetection: false,
```

Once it's off, neither the cookie nor `Accept-Language` plays a part: `/` is always the default locale, and the locale is decided only by the URL prefix and the switcher.

### SEO

Automatic redirects don't affect Google's crawling: Googlebot [doesn't send `Accept-Language`](https://developers.google.com/search/docs/specialty/international/locale-adaptive-pages), so it always gets the default-locale version. Conversely, Google also **won't** discover `/zh` through the redirect. Each locale version is declared through `<xhtml:link rel="alternate" hreflang>` in the sitemap and hreflang in the pages, pointing at each other (locked by `e2e/i18n/seo.spec.ts`). So **after adding a language, confirm that the sitemap and hreflang include it**; that's how it gets indexed.

## Changing the default language

Change `defaultLocale` in `src/core/i18n/locales.ts` to another locale that's already in `locales`. After the change, URLs for the old default locale get a prefix.

## Copy

- All UI copy lives in `messages/<locale>.json`, type-checked against `en.json`: if `t("...")` uses a wrong key, `pnpm typecheck` reports an error.
- Navigation items in `site.config.ts` (`nav.header`, `nav.footer`) hold keys under `Nav`, not the copy itself.
- For on-site links, use the `Link` exported from `@/core/i18n/navigation`; it adds the current locale prefix automatically.
- Blog posts are stored per locale in `content/blog/<locale>/` and don't fall back to the default locale. If a new locale has no posts, `/zh/blog` is an empty list (noindex). When you translate a post, use the same file name as the original; hreflang links the two.

## Testing

The `i18n` project in `pnpm test:e2e` copies the repository into a temp directory, adds the test locale `de` following the steps above (its copy is generated automatically from `en.json`, prefixed with `[de]`), then builds and starts it, and verifies locale switching, URLs, copy, and the detection priority above (`e2e/i18n/detection.spec.ts`). See `e2e/i18n/serve.ts`.
